# RustServer.PluginCatalog — согласованная концепция

**Статус:** требования и направление развития, **не** задание на немедленную реализацию.

## Назначение

PluginCatalog — персональная веб-библиотека Rust-плагинов вместо большого Excel. Она полезна сама по себе, независимо от запуска Rust-сервера. Позже данные каталога дополняются фактическим состоянием установки, конфигурации и обновлений через другие сервисы.

Приоритеты: **(1)** удобное массовое наполнение из Excel/JSON и сохранность данных, **(2)** организация личной библиотеки и представлений, **(3)** будущий анализ установленного C#-плагина. Проверку опубликованных версий и уведомления **отложить**: они не блокируют создание и использование каталога.

## Организация библиотеки

### 1. Управляемые источники (Sites / Sources)

Примеры текущих источников: **uMod, Codefling, Lone.Design, MyVector, Chaos Addons**. Это **не** жёстко заданный enum: можно создавать, переименовывать и удалять записи источников, а также добавлять новые сайты. Плагин может иметь несколько URL; перенос плагина на другой сайт не должен требовать смены его категорий или статусов. Источник связан с URL, а не с личной классификацией плагина.

### 2. Личные метки / статусы (Library Tags)

Плагин может быть просто добавлен **без меток**. Примеры пользовательских меток:

- `Nice to have` — интересно на будущее;
- `Planned purchase` — хочу купить;
- `Purchased` — куплен;
- `Rejected / Archived` — исключён из использования, не понравился, отложен.

Метки должны быть **управляемыми и допускающими сочетания**: например, `Purchased` + `Rejected`. Не превращать их в один взаимоисключающий enum. Не вводить фиксированные предметные категории `Economy/PvE/Building`.

**Цена — самостоятельная информация** (`amount`, `currency`, при необходимости ссылка на предложение/заметка), и её наличие **не означает покупки**. `Purchased` остаётся личной меткой, **не** отдельным обязательным флагом/разделом. Возможность записать цену у интересующего, ещё не купленного плагина обязательна.

### 3. Пользовательские папки (Folders)

Пользователь самостоятельно создаёт каталоги наподобие `Shop`, `Admin`, `Experiments` и кладёт туда плагины как в закладки. Желательно допускать один плагин в нескольких папках **без дублирования записи**. Названия папок не зафиксированы разработчиком. Вложенность папок — вопрос для будущего уточнения, сейчас не обязательна.

### 4. Состояние на сервере — не метка библиотеки

Нужно показывать, например: `Not installed`, `Installed / not configured`, `Configured`, `Disabled`, `Compilation error`. Статус `Update available` относится к отложенной функциональности отслеживания версий. Факты установки и деплоя должны поступать от `RustServer.Plugins` / смежных сервисов, а не выводиться из метки `Purchased`. В перспективе состояние может различаться по серверам.

## Карточка плагина и контент

- Название, автор, URL-источники, пользовательские заметки. **Не требовать версию и дату обновления** при создании, редактировании или импорте плагина; не показывать их как обязательные свойства карточки.
- **Description:** длинный, редактируемый текст с поддержкой **Markdown**, заголовков, ссылок, списков, блоков кода. Описание может быть первоначально извлечено с сайта, а затем отредактировано вручную. Не ограничивать одним коротким текстовым полем.
- **Media** разделяется по назначению: **иконка** (главная), **превью/скриншоты плагина**, **технические изображения/вложения** для будущей Wiki. В БД — метаданные и ссылки на файлы; файлы хранятся отдельно от release-директорий.
- Можно хранить внешние ссылки на YouTube/видео. Загружать/хранить видеофайлы сейчас не требуется.
- **Wiki пользователя** для инструкций и дополнительного контента — будущая возможность, не текущая задача.

## UX

Основной сценарий — работа с большой библиотекой, а не постоянное создание записей. Нужны удобные представления (таблица/список), фильтры по источникам, меткам, папкам и состоянию установки; в перспективе сохранённые views и настраиваемые колонки. Не перегружать строки кнопками: открытие карточки, добавление и контекстные действия; опасные действия — с подтверждением.

Для пользовательских меток можно автоматически выбирать цвет из палитры **и сохранять его**; конкретная цветовая семантика состояний ещё не согласована. Не назначать новый случайный цвет при каждом отображении.

## Наполнение каталога через JSON (приоритет до парсеров сайтов)

**Цель:** быстро перенести существующий Excel и добавлять сразу много плагинов без ручного заполнения каждой карточки. **Один JSON-файл = коллекция `plugins`**, а не один файл на каждый плагин. JSON — **формат ввода данных**, а не дамп PostgreSQL и не замена резервной копии БД и медиа.

### Web UX

- В каталоге предусмотреть действие **Import JSON**: загрузить **один `.json` с массивом `plugins`**. Даже один плагин передаётся как массив с одной записью; формат одиночного объекта на корне не требуется.
- В этом же окне — **Download example JSON** (валидный образец коллекции) и доступное описание полей **Required / Optional**. Образец должен быть пригоден для передачи LLM вместе с Excel. **Требования и актуальный образец для разработки находятся в одном этом документе**, ниже; отдельный файл-приложение для передачи агентам не нужен. В будущем UI выдаёт JSON-образец прямо из окна.
- Перед сохранением показывать **preview**: количество записей, разобранные значения, ошибки валидации, неизвестные источники/метки/папки и предполагаемые дубликаты. Пользователь подтверждает импорт; не выполнять молчаливое перезаписывание существующих данных.
- При совпадении записей предлагать пропустить или явно сопоставить/обновить; **не плодить дубликаты**. Для новых записей без ID ориентироваться прежде всего на известные URL; неоднозначные совпадения требуют решения пользователя.
- После импорта показать результаты: создано / пропущено / ошибки. Не принимать частично повреждённый JSON молча.

### Предлагаемый входной формат v1

Контейнер: `{ "schemaVersion": 2, "plugins": [ ... ] }`. `plugins` — **коллекция** произвольного размера. `schemaVersion` нужен для будущей эволюции формата импорта; это **не версия плагина и не версия схемы PostgreSQL**. Пример JSON встроен ниже в этот документ (позже — скачивается из Web).

| Поле | Обязательность | Назначение |
|---|---|---|
| `schemaVersion` | **Required** | Версия формата JSON (первоначально `2`) |
| `plugins` | **Required** | Массив объектов; минимум один плагин |
| `plugins[].name` | **Required** | Название; единственное обязательное пользовательское поле плагина |
| `plugins[].sources` | Optional | Список URL, необязательных названий сайтов и подписей (`{ "url", "site", "label" }`); при наличии записи URL обязателен |
| `plugins[].author` | Optional | Автор плагина |
| `plugins[].description` | Optional | Полный текст в **Markdown** |
| `plugins[].notes` | Optional | Личные заметки |
| `plugins[].sourceDescription` | Optional | Описание источника в Markdown |
| `plugins[].price` | Optional | `{ "amount": number, "currency": "USD" }`; сумма и валюта указываются вместе; **не означает `Purchased`** |
| `plugins[].tags` | Optional | Массив имён пользовательских меток, включая `Purchased`, если пользователь действительно отметил покупку |
| `plugins[].folders` | Optional | Массив имён пользовательских папок; без дублирования записи плагина |

Неизвестные метки, папки и сайты должны быть обнаружены на этапе preview; пользователь решает, создавать ли их или сопоставить с имеющимися. При импорте нельзя автоматически проставлять покупку, фактическую установку, конфигурацию или успешный деплой. **Не передавать** `id` или `slug` из Excel/LLM: `slug` автоматически выводится из `name` по действующим правилам; внутренний ID записи создаёт сервер. При одинаковых/сходных названиях и совпадающих URL импорт показывает конфликт до записи, а не незаметно перезаписывает плагин. Файлы иконок/скриншотов этим простым JSON-импортом **не загружаются** — это отдельный механизм работы с медиа.

Если текущий API требует дополнительных полей (например, `slug` или `description`), слой импорта должен согласовать это с контрактом при реализации, **без вымышленных содержательных значений**. Данные, относящиеся к проверке версии, из импортируемого JSON не требуются. Данный формат — согласованное **UX/предметное требование**, не утверждение о текущем DTO/API.

### Встроенный пример JSON-коллекции v1

Этот пример одновременно служит образцом для будущей кнопки **Download example JSON** и шаблоном, который можно передать LLM с Excel. Все примеры вымышленные; URL не претендуют на реальные страницы плагинов.

```json
{
  "schemaVersion": 2,
  "plugins": [
    {
      "name": "Example Shop Plugin",
      "sources": [
        {
          "site": "Example Site",
          "label": "Listing",
          "url": "https://example.com/plugins/shop"
        }
      ],
      "author": "Example Author",
      "description": "## Overview\nExample **Markdown** description.\n\n```csharp\n// Code example\n```",
      "notes": "Interested, but not purchased yet.",
      "sourceDescription": "## Source notes",
      "price": {
        "amount": 14.99,
        "currency": "USD"
      },
      "tags": ["Nice to have"],
      "folders": ["Shop", "Experiments"]
    },
    {
      "name": "Example Purchased Plugin",
      "price": {
        "amount": 9.50,
        "currency": "EUR"
      },
      "tags": ["Purchased", "Rejected"],
      "folders": ["Archive"]
    },
    {
      "name": "Example Minimal Plugin"
    }
  ]
}
```

В примере цена у первого плагина **не означает**, что он куплен; второй плагин одновременно `Purchased` и `Rejected`. В JSON намеренно **нет полей версии, даты обновления, `id` или `slug`**.

### Использование с LLM

1. Скачать JSON-образец и правила полей из окна импорта (до появления UI — взять встроенный пример из этого документа).
2. Передать LLM образец, правила и Excel; попросить преобразовать **все строки в один массив `plugins`**. Отсутствующие данные опускать, ничего не придумывать; **не ставить `Purchased` по наличию цены** и **не генерировать `id`/`slug`**.
3. Загрузить **один** полученный JSON в Web, проверить preview и подтвердить импорт. Большие книги Excel допускается конвертировать частями (отдельными коллекциями) с проверкой дубликатов при каждом импорте.

Этот сценарий **раньше разработки HTML-парсеров**: он позволяет сразу начать миграцию с Excel, а парсеры впоследствии дополнят/обновят метаданные по URL.

## Будущие возможности (не входят в текущий импорт)

### Сканирование установленного C#-плагина

Позднее: по **конкретной установленной версии** анализировать `.cs` и, при необходимости, конфигурацию для поиска команд, permissions и групп. Отчёт можно посмотреть и **по решению пользователя сохранить** в БД. Данные имеют переменную структуру и длину; `PostgreSQL jsonb` — возможный формат для результатов сканирования, если по отдельным полям не нужен поиск. Статический анализ не гарантирует обнаружения команд/permissions, создаваемых динамически или задаваемых конфигурацией.

### Проверка версий и уведомления — отложены

Версию **не включать** в JSON-импорт и не использовать как основное обязательное поле плагина. Версия на сайте автора, версия исходников в Git и версия, фактически развёрнутая на сервере, могут не совпадать. Это **три разных контекста**, а не одно значение `Plugin.Version`.

Когда проверка обновлений станет актуальной, использовать связанный URL и отдельный site parser: `PluginId → URL → HTTP HTML → опубликованная версия и дата обновления`. Парсер читает HTML без исполнения JavaScript и без CSS-рендеринга; правила заранее проверяются на реальной HTML-странице сайта. Версии/даты, которые невозможно достоверно извлечь, **не выдумывать**. Уведомления проектировать позднее, вместе с сопоставлением опубликованной и реально установленной версий.

## Сохранность данных и развитие схемы

- Каталог будет большим; нельзя заставлять пользователя повторно вводить данные после каждого релиза или пересоздания тестовой VM.
- Изменения структуры БД — **версионированные миграции** с сохранением существующих записей.
- Бэкап включает **БД и медиа**; хранится **вне уничтожаемой VM**. Перед опасным обновлением — резервная копия, после успешной миграции — актуальная копия.
- **Полный ZIP-экспорт каталога с медиа** доступен через API; восстановление между независимыми установками остаётся будущей задачей; JSON-импорт для наполнения из Excel — другая задача. Ни то ни другое **не подменяет миграции** при обычном обновлении существующей базы.

## Границы текущего этапа

Этот **единственный документ** фиксирует предметную модель, контракт JSON-коллекции и пример для переноса Excel. Он не требует передачи отдельного JSON-файла как приложения. Документ фиксирует направление развития. Не менять текущий UI-заказ агенту, не начинать отдельные серверные работы, JSON-импорт, Wiki, парсеры или сканер без следующего согласования. Детали хранения, конкретные DTO/таблицы и цветовые правила можно определить перед реализацией.
