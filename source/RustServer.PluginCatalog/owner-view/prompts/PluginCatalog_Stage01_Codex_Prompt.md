### Согласованный проект и назначение

Новый репозиторий и микросервис **`RustServer.PluginCatalog`**. Независимая библиотека плагинов Rust: список плагинов, имя, версия, источники/сайты, описание, дата последнего обновления автором и медиа. В перспективе карточки с галереями, GIF/видео, внутриигровые preview, а также совместное отображение с установленными плагинами. Каталог не обязан содержать только установленные плагины.

Разделение ответственности:

- `RustServer.Plugins` — Git, отслеживание реальных файлов, Staging/Production, Release, Deploy.
- `RustServer.PluginCatalog` — каталог, источники, известные версии, метаданные и медиа.
- `RustServer.Versions` — версии серверного ПО (существующее назначение).
- `RustServer.Web` — интерфейс, на следующих этапах список и карточка каталога.
- `RustServer.Platform` — Bootstrap, системная установка и развёртывание.

### Полный план — 9 последовательных промптов

### Обязательная архитектура

**Feature-Based Architecture + Command Handlers + Orchestration + Ports & Adapters**. Чистое дерево каталогов с понятными корнями функций/фич; компактный `Program.cs` только как стартовый композиционный корень, без бизнес-логики и inline handlers. DI и map endpoints выносятся в явные extension/registration classes.

### Порты и реализации

- **Database Port** → в первой реализации PostgreSQL; позже возможны MS SQL Server или отдельный API-адаптер/сервис.
- **Media Storage Port** → в первой реализации Local Filesystem; позже S3 или отдельный Storage API/сервис.
- Сейчас **не создаём** дополнительные микросервисы базы/медиа. Не пишем MS SQL/S3-адаптеры без необходимости, но бизнес-логика не должна зависеть от технологий хранения.

### Данные

Начиная с первых итераций планируем связанные сущности:

- `Plugin`: Id, Name, Slug, Description, CurrentKnownVersion, LastPublishedAt (дата обновления автором, если известна), CreatedAt/UpdatedAt записи в каталоге.
- `PluginSource` (1:N): несколько ссылок одного плагина — сайт, GitHub, Codefling/uMod, документация, потенциальный URL поиска версии.
- `PluginMedia` (1:N): иконка, скриншоты, GIF, видео/превью, тип, подпись, порядок, StorageKey.
- `Plugin.IconMediaId` — явная ссылка на главную иконку, чтобы страницы каталога и будущий список установленных плагинов могли получить её сразу в составе DTO. Не требовать наличие иконки при создании плагина.

Версия — известная версия в каталоге, **не установленная** на игровом сервере. Дата публикации автором и дата редактирования записи каталога — разные вещи. Возможные будущие `PluginInstallations`, категории, теги, авторы, история версий — **не реализуем сейчас**. Связь с установленными плагинами будет проектироваться отдельно, с опорой на стабильные ID и стратегию сопоставления.

### Где хранить файлы

Не хранить двоичные изображения и GIF как BLOB в БД. Медиа располагаются в постоянном каталоге **вне релизов** (например, `/var/lib/rustserver/plugin-catalog/media/{pluginId}/{mediaId}/original.png` и `thumbnail.webp`). В БД — метаданные и переносимый относительный `StorageKey`, **не абсолютный путь и не прямой физический S3 URL**. Данные медиа, PostgreSQL и конфигурации должны резервироваться независимо от приложения и игровых snapshots.

### Future Portable Data Migration

В будущем потребуется **собственный инструмент переноса** `RustServer.DataMigration` (возможно, CLI) между серверами и провайдерами:

- PostgreSQL → PostgreSQL;
- PostgreSQL → MS SQL Server;
- Local Filesystem → S3;
- S3 → Local Filesystem/другой S3.

Это логический экспорт каталога вместе с медиа, **а не просто pg_dump**. Будущий процесс: `Export → Import → Validate → Switch → Rollback`. Портативный формат может включать manifest с версией формата и checksum, JSON данных и папку медиа. Перенос должен сохранять стабильные PluginId, MediaId, StorageKey, проверять данные и переключать конфигурацию только после валидации, с возможностью отката. **Сейчас инструмент не реализуем**, но не закрываем возможность его появления архитектурой.

### Обязательные правила работ

- Следовать `AGENTS.md` и архитектуре, поддерживать документацию и changelog.
- Держать `Program.cs` чистым, фичи изолированными и древовидными.
- **Тесты минимальные**: один небольшой репрезентативный позитивный сценарий (happy path/smoke) на основную работу очередного этапа; без матрицы негативных сценариев, сложных fixture и попыток достичь высокого процента покрытия, если владелец отдельно не попросил. На этапе 1 тесты не нужны. Тесты не должны занимать половину разработки.
- Работы с инфраструктурой — через Platform / Bootstrap; на текущем этапе не менять их.
- Пока нет production и ценных данных, не накапливать миграции EF Core ради каждой переделки: можно пересоздавать dev-схему. Когда появятся ценные данные, нужен контролируемый способ развития схемы, сохранения и переноса данных.
- **Production не зависит от development** и собирается/развёртывается из зафиксированных артефактов.

### Не входит в первую реализацию

- Прямая установка/Deploy плагинов из каталога.
- Реализация MS SQL, S3 и дополнительного storage/database микросервиса.
- Реализация инструмента Data Migration.
- Сложная тестовая инфраструктура и расширенное покрытие.

## 2. Создай или аккуратно дополни `AGENTS.md`

Этот файл нужен агентам и должен быть **кратким, строгим и операционным**, не копией owner-view. Сохрани существующие правила репозитория, если они есть. Обязательно включи:

1. Обязательные ссылки на `owner-view/PROJECT_PLAN.md` (цель, этапы, границы) и `docs/architecture.md` (технические правила). Читать перед кодингом.
2. Feature-Based + Command Handlers + Orchestration + Ports & Adapters. Каждый функциональный блок имеет **свой корень** в иерархии; внутри Commands, Queries, Domain, Ports, а адаптеры технологий в Infrastructure. Не делать плоский `Services/` с десятками несвязанных классов.
3. `Program.cs` — только минимальный composition entry point (создание builder, вызов DI-модулей, pipeline, map endpoints, Run). Без inline routes, handler-логики, SQL/файловой логики.
4. Controllers/Endpoints максимально тонкие: transport mapping → handler. Handler организует сценарий; ports абстрагируют IO; adapters реализуют интеграцию с хранилищем и внешними системами.
5. **Минимальная тестовая политика:** только небольшой happy-path/smoke на главный сценарий очередной реализованной функциональности. Не плодить negative/boundary/combinatorial тесты, сложные моки и snapshots, пока явно не запрошено. На документационные изменения тесты не писать. Не обещать «100% coverage».
6. PostgreSQL/Local — текущие адаптеры, MS SQL/S3/удалённые сервисы — будущие; домен не зависит от конкретного provider. IDs и StorageKey переносимые.
7. Не менять другие репозитории без отдельного этапа. Для Bootstrap идти через `RustServer.Platform`. Не вводить production-зависимости от develop-ветки или локальных путей.
8. Сначала архитектура и документация, затем код; фиксировать принятые решения и обновлять changelog, когда требуется.
9. Не реализовывать задачи следующих этапов в текущем. Избегать overengineering и бесцельных абстракций.

## 3. Зафиксируй техническую архитектуру в `docs/`

Создай компактные, но достаточные документы:

- `docs/architecture.md`: границы микросервиса, feature tree, поток «HTTP endpoint → Command/Query Handler → Port → Adapter», DI, Program.cs composition root, примеры сценариев **без реализации кода**.
- `docs/data-model.md`: сущности и связи (Plugin, Sources, Media, IconMediaId), поля и значения, отличие версии каталога от установленной версии, расширение без преждевременных таблиц.
- `docs/api-contract.md`: **черновой** REST API (CRUD, list/search/filter/page, sources, media, icon, URL доступа); концепция DTO и ошибок без генерации OpenAPI в этом этапе.
- `docs/storage-and-migration.md`: портативный StorageKey, локальный каталог, резервирование, планы MS SQL/S3 и будущего Export/Import/Validate/Switch/Rollback. Явно отметить, что future adapters/tools пока не реализуются.

Предложи **пример целевой структуры**, например:

```text
src/RustServer.PluginCatalog.Api/
  Program.cs
  CompositionRoot/
    DependencyInjection.cs
    EndpointRegistration.cs
  Features/
    PluginCatalog/
      Plugins/
        Commands/
        Queries/
        Domain/
        Ports/
      Sources/
        Commands/
        Queries/
      Media/
        Commands/
        Queries/
        Ports/
  Infrastructure/
    Persistence/PostgreSql/
    MediaStorage/Local/
```

Это иллюстрация: адаптируй названия к существующим конвенциям, не создавай файлов кода. Избегай дополнительных пустых слоёв и интерфейсов без потребности. Документируй, где будет находиться feature entry point и его DI-регистрация. Учитывай, что позже доменная часть может быть вынесена в отдельный сервис без переписывания API-контрактов.
