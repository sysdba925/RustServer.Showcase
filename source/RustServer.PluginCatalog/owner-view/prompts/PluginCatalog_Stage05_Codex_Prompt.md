## Цель и приёмочный сценарий

Оператор может создать Plugin через API Stage 04, загрузить PNG/JPEG/WebP/GIF как медиа плагина, выбрать его главную иконку, получить список галереи/детали с `accessUrl`, открыть байты изображения через API, отредактировать подпись/порядок, удалить медиа, не оставив битую ссылку у Plugin, и после рестарта API получить сохранённые файлы по прежним стабильным идентификаторам. Пользователь позже сможет применить те же URL для сайта и внутриигровых превью. В Stage 05 Web UI нет.

## Архитектура

Соблюдай **Feature-Based Architecture + Command Handlers + Orchestration + Ports & Adapters**. Функциональный корень остаётся `Features/PluginCatalog`; внутри добавь `Media/Commands`, `Media/Queries`, `Media/Transport` и необходимые `Ports`. Оркестрация жизненного цикла медиа — в handlers; SQL только в PostgreSQL adapter, файловые операции только в Local adapter. Для байтов создать конкретный storage port, например `IPluginMediaStorage`, с операциями сохранения/чтения/удаления, нужными реальным сценариям. Расширять **существующий** persistence port `IPluginCatalogStore` только на необходимые операции медиа. `Program.cs` — по-прежнему только composition flow. DI, регистрация endpoint-ов и конфигурация — по существующему образцу, не инлайн в Program. Не создавать framework, mediator, глобальные слои и общие `Service`-классы «на будущее».

`MediaStorage.Provider=Local` — единственная работающая реализация сейчас; техническая граница обязана допускать будущие S3 и Storage API adapter без переделки handler или публичного API. Не писать S3 клиент и не делать сетевой storage микросервис сейчас. Не помещать бинарные данные в PostgreSQL. Не включать абсолютный путь, S3 URL или `StorageKey` в публичные DTO.

## Local Filesystem и конфигурация

- Локальный root настраиваемый, а не вычисляемый от assembly/current release/checkout. Целевой persistent path для будущего Platform: `/var/lib/rustserver/plugin-catalog/media/`; это **целевое соглашение**, а не команда менять VM или Bootstrap на Stage 05.
- Для локального Development допустим отдельный явно конфигурируемый каталог внутри игнорируемого `.local/`. Не хранить бинарные файлы в Git, `wwwroot`, каталогах `bin/obj`, `releases` или под директориями плагинов игрового Rust Server.
- `StorageKey` должен оставаться переносимым относительным POSIX-подобным ключом, например `{pluginId}/{mediaId}/original.png`; root задаётся адаптеру конфигурацией. Выбери и документируй **одно** правило о включении/невключении префикса `media/`, не используй несовместимые варианты одновременно.
- Физический путь — только результат безопасного соединения `root + validated StorageKey`; запретить `..`, абсолютные пути, обратные слэши, traversal и выход через симлинки. Имя загруженного пользователем файла не использовать как путь. StorageKey генерирует сервер из ID и подтверждённого формата.
- Запись через временный файл и атомарное завершение там, где возможно; не оставлять частичный доступный оригинал. Корректные async IO, cancellation и освобождение потоков.
- Проверить права/доступность хранилища при выполнении операций, но **не** ломать `/health` и не требовать наличие media root для запуска процесса. Ошибки storage — контролируемые, без раскрытия локальных путей клиенту.
- Не создавать systemd unit, production directories/users, PostgreSQL provisioning, Bootstrap scripts и backup jobs: это Stage 08.

## Модель и API

Сохрани существующую семантику `PluginMedia` (`Id`, `PluginId`, `Kind`, `Caption`, `SortOrder`, `StorageKey` XOR `ExternalUrl`, `ContentType`) и `Plugin.IconMediaId` (иконка относится **к тому же Plugin** и имеет Kind `Icon`). Добавь доменные методы изменения разрешённых полей, а не прямые сеттеры из endpoint. Не заменяй `Guid`, не меняй существующие идентификаторы при изменении медиа. Обеспечь предсказуемую сортировку галереи по `SortOrder`, затем `Id`.

Согласовать, документировать и реализовать медиа-маршруты черновика `docs/api-contract.md`:

- `GET /api/plugins/{pluginId}/media` — упорядоченная галерея.
- `POST /api/plugins/{pluginId}/media` — multipart upload оригинала с `kind` (иконка/скриншот/animated preview в рамках поддерживаемых типов), optional `caption`, `sortOrder`.
- `PUT /api/plugins/{pluginId}/media/{mediaId}` — редактирование метаданных, а не повторная загрузка файла.
- `DELETE /api/plugins/{pluginId}/media/{mediaId}` — удаление медиа, в том числе корректная обработка выбранной иконки.
- `PUT /api/plugins/{pluginId}/icon` — назначить существующий Icon-media или снять выбор. Отдельное медиа загружать для назначения не нужно.
- `GET /api/plugins/{pluginId}/media/{mediaId}/content` — выдача байтов оригинала с правильным `Content-Type`, пригодная для браузерного `<img>` и GIF.

Расширь **существующие** `GET /api/plugins` и `GET /api/plugins/{pluginId}`: в `PluginSummaryDto.icon` должны появляться ID/`accessUrl`/тип выбранной иконки (или `null`), в `PluginDetailsDto` — `iconMediaId` и `media[]` с корректными URLs, даже после рестарта. Не создавать N+1 запрос на каждую иконку списка; получение иконок/галереи должно быть спроектировано с нормальной выборкой и пагинацией. Сохранить ранее опубликованные имена полей, существующий CRUD Plugin/Source и семантику сортировки/фильтров. `StorageKey` и filesystem path не попадут в JSON.

`PluginMedia` уже допускает `ExternalUrl` для внешнего видео/превью. Выбери понятный минимальный операторский способ добавлять/удалять такую запись (например отдельный JSON endpoint, не смешивая JSON и multipart), **без скачивания/проксирования стороннего контента**. При необходимости расширь черновой контракт, отразив `accessUrl` или external link в DTO без подмены его внутренним StorageKey. Загрузка бинарных видео не входит в этот этап. Не открывать arbitrary URL fetch и SSRF через сервис.

API HTTP ошибки: сохранить `application/problem+json` + machine-readable `code` как в Stage 04. `404` если plugin/media не существует или медиа чужое; `400` для неверных полей; `413` для превышенного размера; `415` для запрещённого типа; корректный `409` при несовместимых состояниях. Не отдавать stack traces, имена SQL constraints и физические пути. Явно и синхронно обновить OpenAPI schema и `docs/api-contract.md`.

## Работа с изображениями и thumbnails

- В первой версии поддержи оригиналы PNG, JPEG, WebP и GIF. Для внешних видео — только ссылка, не файл. SVG, HTML, EXE и произвольные бинарные данные не принимать. Используй whitelist и **проверяй фактический формат/декодируемость файла**, а не доверяй расширению, имени и одному `Content-Type` клиента.
- Установи и задокументируй разумные лимиты размера upload и (если используется декодер изображений) пикселей/кадров; избегай декомпрессионных бомб и неограниченного чтения памяти. Настрой HTTP/multipart limits согласованно.
- Сохраняй оригинал без изменений; генерируй отдельный статичный thumbnail (WebP или другой документированный поддерживаемый формат) для списков/галереи. Для GIF оригинал остаётся анимированным, thumbnail может быть первым кадром. Иконку на страницах API можно отдавать в пригодном варианте (thumbnail) при сохранении URL оригинала для полноэкранного просмотра. Для thumbnail допускается детерминированный вариант рядом с оригиналом, без отдельной таблицы, если это согласуется с текущей схемой и описано в документах.
- Выбирая image-processing библиотеку, проверь поддержку .NET 10/Linux, возможность работы на Ubuntu и условия лицензирования. Не реализуй собственный декодер. Не тащи тяжёлую зависимость без необходимости.
- Опиши caching для контента и thumbnail и способ изменения URL/инвалидации, не допуская показа устаревшей версии при замене файла; не требуется отдельный CDN или background worker.

## Целостность и удаление

Файловая система и PostgreSQL **не образуют общую транзакцию**. Зафиксируй и реализуй минимальную безопасную orchestration:

1. Upload: сохранить байты в storage → записать метаданные в PostgreSQL → при неуспешной записи метаданных попытаться удалить новый файл/thumbnail, а ошибку cleanup залогировать. Нельзя успешно вернуть API-ответ при битой ссылке.
2. Delete: безопасно убрать ссылку/метаданные в DB и после подтверждения удалять файлы; при неуспешном физическом удалении возможен orphan file, но не должна появляться запись БД, указывающая на удалённые байты. Задокументировать процесс cleanup/повторного удаления orphan (автоматический job не обязателен).
3. Удаление выбранной иконки сначала **снимает `IconMediaId` в той же DB-транзакции**, затем удаляет media metadata, учитывая существующий composite FK + `Restrict`. Проверить порядок EF изменений, при необходимости применить одну транзакцию или безопасную атомарную операцию.
4. Сохранить Stage 04 правило `DELETE Plugin → 409 plugin_has_media`, пока галерея не очищена. Не допускать silent cascade удаления физических файлов.
5. Все действия по media проверяют ownership (`media.PluginId == route pluginId`) и не открывают доступ к произвольному StorageKey.

## Тестирование и проверка

Тесты **минимальные**, согласно `AGENTS.md`: 1–2 репрезентативных позитивных smoke/happy-path теста: загрузка→чтение→назначение иконки→детали/list; при возможности удаление выбранной иконки. Не создавать громадную матрицу test cases, mocks и фикстур. При этом необходимые проверки безопасности upload/path/type обязаны быть реализованы в production code, даже если для каждой нет отдельного теста.

Запустить `dotnet restore`, `dotnet build`, `dotnet test`. Убедиться, что `/health` работает **без БД и без готового media directory**, и OpenAPI в Development публикует реальные маршруты + корректные multipart schemas, но не публикует их в production.

**Незакрытая проверка этапов 3–4:** реальная PostgreSQL integration-проверка ещё не проводилась. Если имеется явно выделенная disposable Development PostgreSQL DB и connection string, выполни сквозной smoke (создание схемы отдельным DevSchema tool, CRUD Plugin/Source, upload, GET content, icon selection, restart/persistence). Никакого `EnsureDeleted` или сброса чужой БД; не трогай production. Если PostgreSQL недоступен — не устанавливай его сам и не симулируй, будто интеграция проверена: в отчёте явно укажи блокер и что проверено без PostgreSQL. Это не разрешение переходить к Stage 08.

**Важная безопасность:** Stage 04 API не имеет authentication/authorization. Stage 05 не должен публиковать upload API наружу как production-ready, не открывать public network listener для проверки и не изобретать самовольную auth-схему. В README оставь видимое требование надёжной authn/authz границы **до публичного production-доступа** (решение согласуем отдельно).
