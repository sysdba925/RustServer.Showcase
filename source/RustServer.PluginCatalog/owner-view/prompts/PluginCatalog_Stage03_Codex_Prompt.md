## Что реализовать

### 1. Модели и отношения

Подготовь реальные типы каталога (без HTTP DTO и без EF-аннотаций в Domain) в feature-дереве. В основе — три сущности:

- `Plugin`: стабильный переносимый ID, `Name`, `Slug`, `Description`, `CurrentKnownVersion?`, `LastPublishedAt?`, `IconMediaId?`, `CreatedAt`, `UpdatedAt`.
- `PluginSource`: стабильный ID, `PluginId`, `Kind`, `Url`, `Label?`.
- `PluginMedia`: стабильный ID, `PluginId`, `Kind`, `Caption?`, `SortOrder`, `StorageKey?`, `ContentType?`.

Имена, обязательность и ограничения согласуй с `docs/data-model.md`. Для новых записей разумный выбор — `Guid`/UUID как стабильный ID, UTC timestamps и нормализованный lowercase `Slug`; зафиксируй окончательные решения документально. `LastPublishedAt` означает обновление у автора, а не изменение записи в нашей БД. `CurrentKnownVersion` — **известная версия в каталоге**, не версия установленного Rust-плагина.

Связи: `Plugin` 1:N `PluginSource`, `Plugin` 1:N `PluginMedia`, необязательная ссылка `Plugin.IconMediaId → PluginMedia.Id`. Предусмотри запрет случайного каскадного удаления через главную иконку; правила, что иконка принадлежит тому же Plugin и имеет правильный `Kind`, должны быть описаны (БД-ограничение там, где оно разумно, и будущая проверка через handler на этапе 5). Установку плагинов на Rust-сервере здесь не моделировать.

**Проверь до фиксирования схемы:** будущие медиа включают не только локально загруженные картинки/GIF, но и потенциальные внешние видео. Если текущего `StorageKey` для этого недостаточно, документируй и добавь минимальную совместимую возможность внешней ссылки (`ExternalUrl?` либо обоснованный эквивалент). Не реализуй сам просмотр видео или загрузку файлов. Если нужны ключи превью, предусмотренные планом, опиши место хранения вариантов без добавления неоправданной системы трансформаций.

### 2. EF Core + PostgreSQL adapter

- Используй совместимые с `net10.0` стабильные версии `Microsoft.EntityFrameworkCore` и `Npgsql.EntityFrameworkCore.PostgreSQL`; не смешивай major-версии EF и провайдера.
- Добавь один `PluginCatalogDbContext` и конфигурации EntityTypeConfiguration (либо эквивалент), размещённые в `Infrastructure/Persistence/PostgreSql/`.
- Настрой внешние ключи, уникальный `Slug`, обязательные поля, индексы по реальным запросам каталога, максимальные размеры строк там, где оправданно; не добавляй преждевременные индексы «на все случаи».
- PostgreSQL-specific типы и EF API остаются внутри Infrastructure. Domain не знает ни SQL, ни EF, ни provider; публичные DTO не содержат абсолютных путей или физического S3 URL.
- Зарегистрируй DbContext через DI в composition root / техническом модуле, не размещая SQL и настройки внутри `Program.cs`.
- Connection string берётся из конфигурации / environment variables, не коммитится с паролями. Запуск `/health` не должен требовать доступной PostgreSQL и не должен выполнять SQL.
- **Не создавай `IPluginRepository` и прочие ports только ради архитектурной симметрии.** `AGENTS.md` требует вводить port вместе с первым реальным handler. Непосредственное использование DbContext внутри persistence infrastructure допустимо на этом этапе; интерфейс репозитория для use case появится вместе с ним на этапе 4. Не создавай фиктивный CRUD ради теста.

### 3. Создание dev-схемы без истории migrations

Проект пока не имеет production-данных. **Не создавай цепочку EF Core migrations и `Migrations/`**, если отсутствует явно согласованная необходимость. Опиши простой, явный, **только development** способ создать пустую схему из модели (например, одноразовый сценарий на основе `EnsureCreatedAsync`, но не разрушающий код при каждом запуске).

Критические требования:

- Не вызывай `EnsureDeleted`, не очищай существующие данные автоматически.
- Не выполняй `EnsureCreated`/создание таблиц незаметно при обычном старте API, особенно вне Development.
- Способ инициализации должен быть минимальным: не добавляй ещё один большой микросервис или инфраструктурный проект ради одной dev-команды.
- Ясно напиши в README, что подход `EnsureCreated` — только для временных dev-баз; его нельзя бесшовно смешать с историей EF migrations. До появления ценных данных допускается вручную пересоздать **только специально выделенную dev-БД**. После этого потребуется отдельная управляемая процедура.
- Если доступного PostgreSQL нет, не выдавай модельную проверку за реальный тест создания таблиц. Укажи, что проверено, а что нет. **Не меняй Platform Bootstrap** ради локальной проверки: установка PostgreSQL на чистой VM — этап 8.

### 4. Минимальные проверки

- `dotnet restore`, `dotnet build`, `dotnet test` для всего solution.
- Сохрани существующий smoke test `/health`.
- Добавь **не более одного небольшого нового happy-path теста** на схему/persistence: желательно создание трёх связанных сущностей и успешное чтение через EF в изолированной dev/test PostgreSQL, **только если БД доступна**. Если реальная БД недоступна, используй простую проверку модели EF без тяжёлой инфраструктуры и чётко различай уровень проверки.
- Никаких больших матриц negative/boundary tests, сложных fixtures, Testcontainers, обязательных CI-депендeнси, 100% coverage.
- При доступной локальной dev-БД проверь применение модели, ограничения FK/unique и возможность чтения после записи; не трогай другие БД.
- Повторно проверь `GET /health = 200` без БД и что OpenAPI пока не содержит маршрутов каталога.
