# RustServer.PluginCatalog — Codex Prompt 02/09

## Задача

Реализуй **этап 2 из 9 — запускаемый каркас ASP.NET Core API** в репозитории `RustServer.PluginCatalog`.

Предыдущий этап завершён commit `792765e0dda2370dd370b39dc2d92bd720731b9b`: создана архитектурная документация. Сначала проверь фактическое состояние своего локального репозитория и не уничтожай чужие незакоммиченные изменения. Этот SHA — точка сверки, а не команда сбросить ветку.

**Результат этапа:** минимальный сервис, который локально собирается, запускается, предоставляет `GET /health` и OpenAPI в Development. **Не реализуй каталог плагинов.**

## Обязательная подготовка

1. Прочитай полностью `AGENTS.md`, `owner-view/PROJECT_PLAN.md`, `docs/architecture.md`, `docs/data-model.md`, `docs/api-contract.md`, `docs/storage-and-migration.md`.
2. Проверь соседние сервисы на принятые в RustServer соглашения по SDK, структуре solution, OpenAPI, тестам, README и конфигурации. Используй их как ориентир, но **не копируй инфраструктуру без необходимости**. Не изменяй соседние репозитории.
3. Соблюдай согласованную архитектуру **Feature-Based Architecture + Command Handlers + Orchestration + Ports & Adapters**. Сейчас ещё нет доменных команд/queries, поэтому не создавай заглушки, пустые handlers или фиктивные ports.
4. Не добавляй production-зависимости от `develop`, локальных репозиториев, исходного checkout или runtime-артефактов девелоперской машины.

## Что реализовать

### 1. Структура проекта

- Создай один ASP.NET Core Web API проект под `src/RustServer.PluginCatalog.Api/` и solution в корне. Целевая версия .NET — **`net10.0`**, согласованная с текущим runtime проекта; если локальное SDK несовместимо, сообщи об ограничении, а не меняй версию молча.
- Сохрани возможность расширять дерево `Features/PluginCatalog/{Plugins,Sources,Media}` на этапах 3–5, но **не создавай пустые каталоги и классы ради будущего**.
- Используй `CompositionRoot/DependencyInjection.cs` и `CompositionRoot/EndpointRegistration.cs` (или уже установленный в документах эквивалент): первый отвечает за регистрацию нужных зависимостей, второй — за маршруты и инфраструктурные endpoints.
- `Program.cs` должен быть коротким, только создание builder, вызовы методов composition, сборка приложения, настройка pipeline и `Run()`. Никаких inline route handlers, SQL, доступа к файлам или будущего Plugin CRUD.
- Выбери один консистентный HTTP-стиль для этого каркаса, совместимый с уже описанными тонкими endpoint handlers; не смешивай Controllers и Minimal API без причины.

### 2. Сервисные возможности

- Подключи стандартную конфигурацию ASP.NET Core (appsettings + environment variables). Не добавляй фейковые connection strings, secrets и пока неиспользуемые provider options.
- Настрой DI только для реально требуемых сервисов каркаса.
- Добавь встроенную генерацию OpenAPI для API. JSON документ должен быть доступен в **Development** (например, `/openapi/v1.json`), без обязательного Swagger UI и без тяжёлых дополнительных библиотек, если они не нужны.
- Добавь `GET /health`, возвращающий успешный статус для **liveness** работающего процесса. Эта проверка **не должна** обращаться к PostgreSQL, файловой системе, Rust Server или соседним сервисам. Readiness и dependency checks — не задача этапа 2.
- Обеспечь нормальный запуск через `dotnet run` с локальными безопасными настройками. Порт/адрес не привязывай к production или к не согласованному Bootstrap; укажи конкретную локальную команду запуска в README.
- Не публикуй несуществующие каталожные endpoints в OpenAPI: они остаются проектным черновиком до этапов 4–5.

### 3. Минимальное тестирование

- Добавь **ровно один небольшой автоматизированный smoke/happy-path тест**: вызов `GET /health` возвращает успешный HTTP-ответ.
- Используй простейшую проверяемую тестовую конфигурацию, согласованную с существующим .NET подходом в RustServer; никаких сложных fixtures, матриц негативных сценариев или coverage-требований.
- Проверь `dotnet restore`, `dotnet build` и `dotnet test`. Дополнительно запусти сервис и вручную проверь получение OpenAPI JSON, если среда это позволяет.

### 4. Документация

- Создай/обнови корневой `README.md`: назначение сервиса, требования SDK, точные команды для build/run/test, доступные на данном этапе `GET /health` и OpenAPI, явная пометка «каталог ещё не реализован».
- Обнови `docs/architecture.md` и `docs/api-contract.md` **только по фактически появившимся элементам**: теперь есть каркас, liveness и Dev OpenAPI, а маршруты каталога остаются черновиком.
- Обнови `owner-view/PROJECT_PLAN.md`: этап 1 отмечен завершённым, этап 2 — фактическим результатом после работы, следующий этап — 3. Сохрани исходную таблицу из девяти этапов, не переписывай план.
- Не меняй общие правила `AGENTS.md`, если в них нет реального противоречия с этапом 2. Запрет на создание исходников **на этапе 1** к этапу 2 не относится.
- Зафиксируй существенные изменения согласно существующей политике changelog; не создавай лишнюю документационную структуру.

## Строгие ограничения — НЕ делать в этом этапе

- Не устанавливать PostgreSQL, не подключать EF Core и не создавать таблицы/миграции.
- Не реализовывать `Plugin`, `PluginSource`, `PluginMedia`, repositories, commands/queries, каталог и CRUD.
- Не реализовывать Local/S3 Storage, thumbnails, URL загрузки медиа, экспорт/импорт или `RustServer.DataMigration`.
- Не добавлять Docker, systemd, provisioning, production directories, Bootstrap или деплой в `RustServer.Platform` (это этап 8).
- Не изменять `RustServer.Web`, `RustServer.Plugins`, `RustServer.Versions`, `RustServer.Platform`.
- Не создавать искусственные интерфейсы/слои, общие библиотеки и чрезмерную тестовую инфраструктуру «на будущее».

## Критерии приёмки

1. Есть работающий `net10.0` Web API, solution и понятный README.
2. `Program.cs` минимален; инфраструктурная регистрация и endpoints вынесены.
3. `GET /health` доступен, не зависит от БД или других сервисов.
4. OpenAPI JSON доступен в Development; вымышленных каталоговых endpoints нет.
5. `dotnet build` и единственный smoke test проходят (или указана точная причина невозможности проверки).
6. Документация актуализирована; этап 3 остаётся отдельной задачей.
7. Изменений вне `RustServer.PluginCatalog` нет; production не зависит от development.
